# P1-06 — Command, rendering and audit boundaries

Status: complete locally, 2026-09-04. Parent: `f398f51` (P1-05). Version remains `0.2.9`.

## Implemented contract

- Parameter-bearing IPC commands validate their JSON before provider work or persistence. The gate limits serialized JSON to 1 MiB, depth to 16 and nodes to 50,000. It rejects unknown command/widget/mode shapes, malformed types and out-of-range integers. Queries are capped at 10 KiB, CLI commands at 16 KiB, policy text at 64 KiB, dashboards at 200 unique tiles and known pin collections at 50 entries. Existing per-widget result limits remain; error windows and log-tail windows are bounded to seven days. Draft dashboard inputs remain bounded frontend-owned data; execution validates them again. Selection-region defaults and complete legacy pin snapshots remain supported.
- Fourteen local commands and the existing main-window capability/CSP remain unchanged. A static regression protects local access, explicit permissions, script/connect/frame/form/object restrictions and the command registry. Dependency transport logs are excluded from the platform logger; deliberate app diagnostics use the reviewed surface.
- Production rendering inserts resource text literally. External execution links permit HTTPS only on `console.aws.amazon.com`, `eu-west-1.console.aws.amazon.com` and `us-east-1.console.aws.amazon.com`. Credentials, explicit ports, controls, backslashes and other hosts/schemes are rejected. Unsupported links remain inert and are not copied as trusted console links.
- Each AWS-facing command carries an app-generated audit correlation ID, distinct from the client ID echoed in `_request.id`. An execution `started` event follows the permission gate before credential/identity work. It has one terminal application outcome: `denied`, `succeeded`, `failed` or `cancelled`. Requests denied before execution have no start event. Local-only status reads can complete without starting provider work; later workflow denials can follow a start. Caller drop records logical cancellation. These events express application intent, **not per-wire-call counts or confirmation of remote cancellation**. Capability checks retain a separate `capability_preflight` scope.
- Audit serialization retains only selected structured fields. Raw CLI arguments, input/query bodies, private configuration, arbitrary nested fields and raw error chains are not written. Captured verified account/region may appear in local terminal records; unverified preflight account labels are omitted. SDK codes map to fixed reviewed messages; unknown errors use a fixed generic message. Provider, profile inspection, policy parse/storage and unexpected bridge errors no longer echo source strings. Profile inspection no longer returns the unrelated home-directory field. The intentional local policy editor still receives its own candidate text.
- Partial CodeArtifact/error-chart failures are explicit and retain useful rows. A chart with failed queries no longer implies there were zero errors. Logs Insights timeout reports whether its existing stop request was confirmed, denied, failed or unconfirmed. Error-chart timeouts disclose that remote query status is unknown; no additional remote cancellation mechanism is claimed.
- An audit append failure sets sticky shared health and a visible warning. A later successful write cannot erase evidence of a lost entry. Inspection and policy authorization remain independent of audit availability. Audit read failure preserves the previous UI table. Reading retains at most 1,000 entries and 16 KiB per line, including sanitized legacy rows; full-history scan time and rotation/retention remain P3 work.
- The frontend handles new input-rejection responses as failures rather than successful settings/layout saves. P2 still owns durable storage/I/O outcomes; this unit does not claim that existing storage writes are transactional or reliably reported.
